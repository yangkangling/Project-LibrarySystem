# Architecture Decisions

本文记录图书馆借阅管理系统的关键设计取舍。目标不是把项目包装得复杂，而是说明每个技术选择在当前业务规模下解决了什么问题，以及未来扩展时需要注意什么。

## 1. 为什么使用 Spring Boot

本系统的核心是典型的事务型业务：图书、读者、单册、副本、书架库存、借阅记录之间存在明确的一致性要求。Spring Boot 提供了成熟的 Web、事务、配置、测试和部署体系，能让项目把精力放在业务规则上。

选择 Spring Boot 的原因：

- 约定优于配置，适合课程项目到小型生产系统的平滑升级。
- Spring MVC 能清晰表达管理员端和读者自助端的 REST 接口边界。
- Spring 的声明式事务能覆盖借书、还书、罚款处理这类跨表更新。
- 配置可以通过环境变量注入，便于 Docker、CI 和服务器部署。

取舍：

- Spring Boot 比纯 Servlet 或轻量框架更重，但换来的是工程结构、测试和事务能力。
- 当前版本仍使用 Session 登录，适合单体系统；如果做多实例水平扩展，需要接入 Redis Session 或迁移到 JWT/OAuth2。

## 2. 为什么使用 JPA

系统的数据结构以实体为中心，包含 `Book`、`BookCopy`、`BorrowRecord`、`User`、`StorageLocation` 等稳定模型。JPA 可以减少重复 SQL，并让实体关系、索引和查询方法保持在 Java 代码内可维护。

选择 JPA 的原因：

- CRUD、分页、条件查询能快速实现，减少样板代码。
- 借阅记录需要保留快照字段，JPA 实体能直接表达这些业务字段。
- Repository 接口便于在测试中 mock，也能在集成测试中直接验证数据库状态。

取舍：

- 对复杂报表和高性能聚合，JPA 自动查询不一定最优。
- 当前项目对关键库存扣减没有依赖“先查再存”，而是使用显式 `@Modifying @Query` 条件更新，避免 JPA 脏检查在并发场景下造成超借。

## 3. 为什么借还书使用事务

一次借书不是单表写入，而是必须同时完成：

- 校验读者状态、借阅上限和逾期限制。
- 扣减图书主表 `available_count`。
- 扣减书架库存 `storage_locations.available_count`。
- 占用一本具体单册 `book_copies`。
- 创建借阅记录并回填单册当前借阅记录 id。

这些步骤必须全部成功或全部回滚，否则会出现“记录创建了但库存没扣”“库存扣了但单册没占用”等脏状态。因此借书、还书、批量借还、罚款结清都使用 `@Transactional`。

取舍：

- 事务会增加数据库锁等待，但这是库存系统必须承担的成本。
- 读者行使用悲观锁校验借阅上限，避免同一读者并发请求绕过上限。

## 4. 为什么使用库存原子扣减

借最后一本书是系统里最容易暴露并发问题的场景。如果两个请求同时读取到 `available_count = 1`，再分别保存 `0`，就会产生两条借阅记录但库存只扣一次。

本系统采用条件更新：

```sql
update books
set available_count = available_count - 1
where id = ?
  and status = 'enabled'
  and available_count > 0
```

返回更新行数为 1 才允许继续创建借阅记录；返回 0 表示库存已经被其他请求抢先占用。书架库存和单册占用也使用同样思想，分别通过条件更新保证不会扣成负数、不会把同一本单册借给两个人。

对应测试：

- `BorrowServiceConcurrencyTest.onlyOneReaderCanBorrowTheLastAvailableCopy`
- 同时验证图书主库存、书架库存、单册状态和借阅记录数量保持一致。

## 5. 为什么使用 Session 做权限隔离

系统分为管理员端和读者自助端，两类用户的权限边界不同：

- 管理员可以维护图书、读者、借阅、罚款和书架。
- 读者只能查看和操作自己的借阅记录。

当前版本使用 Session 保存 `adminId` 或 `readerId`，并由 `LoginInterceptor` 在进入控制器前判断接口路径：

- `/self/**` 必须有 `readerId`。
- 其他管理接口必须有 `adminId`。

读者端接口不会接受前端传入的 `userId` 作为身份依据，而是统一从 Session 读取当前读者。例如自助还书会先查询提交记录，再判断所有记录是否属于当前 Session 读者。

对应测试：

- `SelfServiceControllerSecurityTest.readerCannotReturnAnotherReadersBorrowRecord`

取舍：

- Session 对单体系统简单可靠，浏览器使用成本低。
- 多实例部署需要共享 Session；如果要开放移动端或第三方接口，可迁移到 token 方案。

## 6. 为什么升级到 BCrypt 和 DTO

旧版本为了演示方便使用明文密码，这在正式项目呈现上风险很高。当前版本引入 BCrypt：

- 新增用户、默认初始化用户和改密都会写入 BCrypt hash。
- 老数据库中的明文密码仍可登录一次，并在登录成功后自动升级为 hash。
- SQL 初始化脚本也使用 hash，不再插入明文密码。

控制器输入从直接接收实体逐步改成 DTO：

- 图书新增/编辑使用 `BookRequest`，避免前端覆盖实体上的派生字段或只读字段。
- 读者新增/编辑/注册使用专用请求对象，避免前端伪造角色、借阅证号或创建时间。
- 批量借还和读者自助接口补了参数校验，错误信息由统一异常处理返回。

取舍：

- DTO 会增加少量类和字段映射代码。
- 换来的收益是边界更清晰，前端不能随意提交实体字段，后续做 API 文档也更容易。

## 7. 为什么保留单体架构

这个项目的目标是图书馆/资产流转系统，不是微服务演示。当前业务规模下，单体架构更容易保证事务一致性，也更适合课程设计、毕业设计和中小规模部署。

后续如果要扩展为更大系统，可以按以下边界拆分：

- 用户与权限服务。
- 图书与资产主数据服务。
- 借阅/流转事务服务。
- 通知与预警服务。
- RFID/扫码采集网关。

在拆分之前，优先保证领域边界、事务规则和测试覆盖，而不是为了“看起来复杂”提前拆服务。
